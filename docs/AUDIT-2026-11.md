# Auditoría de calidad — DotnetTCG

- **Fecha:** 2026-11-23
- **Alcance:** backend (.NET 10: Api / Application / Domain / Infrastructure), integración Angular, seguridad, rendimiento y cobertura de tests
- **Skills aplicadas:** `clean-architecture-auditor`, `dotnet-clean-architecture`, `project-rules`
- **Método:** lectura de todo el backend + frontend relevante; suite completa con Postgres real (**411/411 verdes, sin skips**); 5 reproducciones a nivel servicio/repo; 8 checks end-to-end por HTTP con `WebApplicationFactory`; 5 reproducciones de Dominio en memoria; verificación de comportamiento contra el source de ASP.NET Core 10. Ningún archivo del repo fue modificado durante la auditoría (los harnesses de reproducción viven en `/tmp/opencode`).

---

## A. Resumen ejecutivo

La arquitectura de dependencias está **bien construida**: Domain sin referencias externas, Application→Domain, Infrastructure implementa abstracciones de Application, Api delgada, DTOs separados de entidades EF, errores de negocio mapeados a HTTP en un solo lugar. Ese es el buen diseño; el problema es que **la corrección en runtime tiene fallas graves en todas las capas**.

| Severidad | Cantidad |
|---|---|
| Crítica | 1 |
| High | 12 |
| Medium | 29 |
| Low | 19 |
| Informational | 4 |

**Los más importantes confirmados:**

1. **Crítico — toda partida iniciada desde el navegador se borra al llegar al tablero** (reproducido end-to-end: `partida existe=False`, `GET /state → 404`).
2. **High — Dominio:** el ataque resuelto vía `PendingChoice` hace 0 de daño y aun así descarta energía; cualquier jugador puede responder el `PendingChoice` ajeno; el costo de energía se valida solo por cantidad (no por tipo); los efectos "hasta el próximo turno" nunca cubren ese turno; un ataque fallido no termina el turno y se puede reintentar; un pending puede clavar la partida e impide conceder. **Todos reproducidos dinámicamente.**
3. **High — Seguridad/disponibilidad:** el rate limiter de auth es **global** (un atacante anónimo bloquea login/registro/recuperación de todos con 20 req/min); un no-miembro puede iniciar cualquier lobby listo (HTTP 200 verificado); excepciones de concurrencia escapan como 500 en vez de 409.
4. **High — Contrato FE↔BE:** el hub caído deja el tablero irrecuperable (throw síncrono + overlay bloqueante); el flujo de espectador en lobby falla siempre.

**Integridad de datos:** mazos borrables en uso (500), lobbies inservibles tras la salida del creador (500), registro concurrente → 500, `CreatedAt` sobrescrito en cada update.

**Limitación principal del gate de calidad:** el repo muestra verde incluso sin base de datos (los tests con DB se auto-omiten y cuentan como pasados) — en la primera corrida, "411 verdes" significó **cero** tests de persistencia ejecutados.

## B. Hallagros

### CRÍTICO

**[FE-001] La partida se borra al navegar del lobby al tablero (ngOnDestroy → LeaveLobby ×2)**

- Severity: **Critical** · Confidence: High · Status: **Confirmed (reproducido end-to-end)**
- Location: `src/DotnetTCG.Frontend/src/app/features/lobby/pages/game-lobby/game-lobby-page.ts:89-95` y `:164-168`; `src/DotnetTCG.Api/Hubs/GameHub.cs:46-62`; `src/DotnetTCG.Application/Games/LobbyService.cs:133-157`

**Evidence**

Las rutas `/lobby/:gameId` y `/game/:gameId` usan componentes distintos; al recibir `game-started` ambas páginas navegan, lo que destruye `GameLobbyPageComponent` y su `ngOnDestroy` invoca `leaveLobby(id)` (fire-and-forget). `LobbyService.LeaveAsync` **no valida `Status`**: saca al jugador de `Players` y, si queda vacío, `games.DeleteAsync` (fila + snapshot + logs).

**Failure scenario**

Ambos listos → auto-start → `game-started` → ambas páginas navegan → `LeaveLobby` ×2 → `remaining.Count == 0` → delete. Reproducido con clientes SignalR reales: `Status=1, jugadores=2` → tras los dos `LeaveLobby`: `partida existe=False, game_players=0` → `GET /v1/games/{id}/state → 404`.

**Impact**

Toda partida jugada desde el FE muere al arrancar. El test existente (`HubLobbyTests.cs:168`) solo hace `LeaveLobby` de **un** jugador y no aserca el estado posterior; el DoD F4 (walkthrough manual) sigue pendiente en el TODO.

**Root cause**

`LeaveAsync` sin guardia de estado + `ngOnDestroy` usado como "salir del lobby" sin distinguir "navegar al tablero".

**Recommended fix**

- (BE) exigir `Status == InLobby` en `LeaveAsync` y que el hub salga del grupo sin tocar `Players` cuando la partida arrancó.
- (FE) no llamar `leaveLobby` en `ngOnDestroy` (solo en `leaveAndGoBack`).

**Regression test**

E2E por hub: ready×2 → esperar `game-started` → `LeaveLobby` desde ambas conexiones → `GET /state` debe seguir 200 y `ExecuteAction` debe funcionar para ambos.

### HIGH

**[BUG-D001] El ataque resuelto vía `PendingChoice` hace 0 de daño y descarta igual tu energía**

- Severity: High · Confidence: High · Status: **Confirmed (reproducido)**
- Location: `src/DotnetTCG.Domain/Engine/Handlers/AttackAbilityHandlers.cs:79-87`; `src/DotnetTCG.Domain/Attacks/AttackPipeline.cs:70-74, 93-100`; `src/DotnetTCG.Domain/Attacks/AttackRegistry.cs:113-115`

**Evidence:** `AttackHandler.Resume` construye un `AttackContext` **nuevo** sin `BaseDamage`/`Damage`; `Pipeline.Resume` salta directo a `ContinueAfterPreChecks`, que usa `context.Damage` (0) y nunca re-invoca `VariableDamage`. `DiscardOptionalCost` sí corre. Repro: Electron Crush con `yes` → **defensor con 0 de daño (esperado 80)**, energía igual descartada.

**Failure scenario:** "Electron Crush" (`NeedsOptionalDiscard`) siempre genera pending en el primer `Execute`; al reanudar, daño = 0. Mismo camino para `NeedsBenchTarget`.

**Impact:** carta real de xy1 inutilizable en su único flujo productivo; pérdida garantizada de energía.

**Root cause:** `Resume` reconstruye el contexto en vez de retomar el calculado; el test `AttackPipelineTests.Resume_WithBenchSelection_Completes:195-212` **enmascara el bug** (reutiliza el mismo `ctx` entre `Execute` y `Resume`).

**Fix:** recalcular `BaseDamage` e invocar `VariableDamage` en `Resume`, o persistir el contexto en `PendingAttack`.

**Regression test:** Electron Crush "50" → `Execute` → responder `yes` → `DamageDealt == 80` y 1 energía descartada (hoy: 0).

**[BUG-D002] Cualquier jugador puede responder el `PendingChoice` ajeno (ChoiceId determinista)**

- Severity: High · Confidence: High · Status: **Confirmed (reproducido)**
- Location: `src/DotnetTCG.Domain/Engine/GameEngine.cs:96-101, 167-200`; `src/DotnetTCG.Domain/Engine/Handlers/TrainerHandler.cs:101-135`

**Evidence:** `Execute` entra en `ExecutePending` **antes** del chequeo de turno y `ExecutePending` jamás compara `action.PlayerIndex` con `pending.PlayerIndex`; solo valida `ChoiceId`. Los ChoiceId son adivinables (`attack:{nombre}:optional-discard`, `trainer:Evosoda:evosoda`). Repro: el rival (PlayerIndex 1) responde el pending del jugador 0 → `Success=true`.

**Failure scenario:** (a) `trainer:` → `ResolveChoice` usa `state.Players[action.PlayerIndex]` (tablero del rival) y busca la carta en **su** mano → efecto en tablero equivocado y tu carta no se descarta; (b) `attack:` → el rival elige por ti objetivo/`yes-no` → descarte fantasma; (c) griefing: cancelar el pending del otro.

**Impact:** rompe la autorización por jugador en el Dominio (la guarda de Application no cubre el hub).

**Fix:** en `ExecutePending`: `if (action.PlayerIndex != pending.PlayerIndex) return "Choice.NotYours"`; considerar ChoiceId no adivinable.

**Regression test:** pending creado por el jugador 0 → respuesta con `PlayerIndex == 1` → error de autorización y pending intacto.

**[BUG-D003] Los efectos `UntilNextTurn` nunca cubren el turno al que apuntan**

- Severity: High · Confidence: High · Status: **Confirmed (reproducido)**
- Location: `src/DotnetTCG.Domain/Game/PokemonInPlay.cs:98-107`; `src/DotnetTCG.Domain/Engine/Handlers/TurnControlHandler.cs:35-43`; `src/DotnetTCG.Domain/Attacks/AttackRegistry.cs:254-283`

**Evidence:** `HasModifier(..., currentTurn)` solo es cierto con `currentTurn <= TurnApplied` y `RemoveExpiredModifiers` lo borra con `currentTurn > TurnApplied`. Aplicado en el turno T del atacante → en T+1 (turno del rival) es `false` y ya se borró. Repro: bloqueo en T = `true`, en T+1 = **`false`**.

**Failure scenario:** Torment, Moonblast (reducción 20), `Prevent`, `RestrictItems`, `PreventRetreat` → efecto no-op en su ventana real. Contraste: `BlockSupporters` sí funciona (usa `untilTurn >= TurnNumber`).

**Impact:** toda la familia de efectos de duración no hace nada (5+ ataques bloqueadores y efectos de carta).

**Fix:** chequeo/expiración con `currentTurn <= TurnApplied + 1` (o `UntilTurn = TurnNumber + 1` explícito). El test `AttackRegistryTests.Torment_BlocksOpponentNextAttack:247` lo **enmascara** (aserta en el mismo turno T).

**Regression test:** Torment en T → `EndTurn` → en T+1 `CanAttack` del defensor → `Attack.Blocked`.

**[BUG-D004] El costo de ataque se valida por cantidad de energía, nunca por tipo**

- Severity: High · Confidence: High · Status: **Confirmed (reproducido)**
- Location: `src/DotnetTCG.Domain/Game/RuleValidator.cs:152-154`; `src/DotnetTCG.Domain/Attacks/AttackPipeline.cs:58`

**Evidence:** `var required = attack.Cost.Count; if (active.TotalEnergyCount < required) ...` — `Cost` es `IReadOnlyList<PokemonType>` y **solo se usa `.Count>`** (las únicas 2 apariciones de `.Cost` en todo Domain). Repro: costo `[Fire,Fire]` con 2 energías Water → `CanAttack` devuelve **`null`** (permitido).

**Failure scenario:** 60+ ataques de xy1 con costo tipado (`Water×3`, `Fire×2`…) se pagan con energía del tipo equivocado.

**Impact:** regla central de pago de energía inexistente.

**Fix:** matching tipo-pago: `Colorless` acepta cualquier energía; el tipo específico exige energía de ese tipo (o comodines DCE/Rainbow según reglas).

**Regression test:** `[Fire,Fire]` + 2 Water → `Attack.EnergyShort`; `[Colorless,Colorless]` + 2 Water → pasa.

**[BUG-D005] Un ataque fallido (Confusión/`FlipToFail`) no termina el turno: se reintenta hasta que salga bien**

- Severity: High · Confidence: High · Status: **Confirmed (reproducido)**
- Location: `src/DotnetTCG.Domain/Attacks/AttackPipeline.cs:55-65`; `src/DotnetTCG.Domain/Engine/GameEngine.cs:223-232, 257-264`

**Evidence:** el fallo vuelve como "error de acción" **antes** de `_turns.EndTurn`; `EnsurePhase` con `type == Attack && Phase == Attack` no bloquea ni transiciona. Repro: confusión en cruz → `Attack.ConfusedSelfHit`, fase queda `Attack`, **segundo intento aceptado** → autodaño acumulado 60.

**Failure scenario:** doc (`docs/game-rules-summary.md:59`): "el ataque falla… **el turno termina**". En código: Hyper Fang en cruz se reintenta hasta cara; la confusión hasta "curarse"; si el autodaño KO, tampoco hay `Resolve` ni premio.

**Impact:** violación explícita de regla + explotación.

**Fix:** distinguir "ataque declarado y fallido" (consume turno, resuelve KO) de error de validación; bloquear reintentos en fase `Attack`.

**Regression test:** atacante confuso con cruz → fase post-acción != `Attack` y un segundo `Attack` debe rechazarse.

**[BUG-D006] Un pending puede clavar la partida; mientras haya pending nadie puede conceder**

- Severity: High · Confidence: High · Status: Confirmed (código)
- Location: `src/DotnetTCG.Domain/Engine/Handlers/TrainerHandler.cs:83-89, 121-122`; `src/DotnetTCG.Domain/Engine/GameEngine.cs:96-101, 143-152`

**Evidence:** `CreateChoice("max-revive")` no valida banca llena; `ResolveChoice` con `Choice.BenchFull` hace `return error` **antes** de `SetPendingChoice(null)` → el pending queda para siempre (la banca no puede cambiar mientras esté). Y `ExecutePending` intercepta **todas** las acciones, incluido `Concede` (el chequeo "salvo Concede" de la línea 99 nunca se alcanza).

**Failure scenario:** banca llena + básico en descarte → Max Revive → `Choice.BenchFull` → ambos jugadores reciben `Choice.Pending` eternamente y no pueden rendirse (el spec dice "CONCEDE anytime").

**Impact:** congelamiento reproducible de la partida; imposibilidad de salir.

**Fix:** validar precondiciones al crear la elección; dejar pasar `Concede` (y `Pause`) en `ExecutePending`.

**Regression test:** banca=5 → `PlayCard(Max Revive)` debe rechazarse sin crear pending; con un pending abierto, `Concede` debe finalizar la partida.

**[BUG-008] El rate limiter "auth" es GLOBAL: cualquier anónimo bloquea login/registro de todos**

- Severity: High · Confidence: High · Status: **Confirmed (source de .NET 10 + repro por HTTP)**
- Location: `src/DotnetTCG.Api/Program.cs:81-91`

**Evidence:** `AddFixedWindowLimiter("auth", ...)` particiona por `PolicyNameKey` (source: `RateLimiterOptionsExtensions.cs`, `RateLimitPartition.GetFixedWindowLimiter(key, ...)`) → **un bucket compartido**, no por IP. Repro con límite 5: cliente A agota 6 logins (`401,401,401,401,401,429`) → **cliente B recibe 429 en su primer login**.

**Failure scenario:** atacante anónimo manda 20 req/min a `/v1/auth/*` → todos los usuarios reciben 429 en login/registro/recuperación de contraseña, indefinidamente. También: 20/min globales es poco para varios usuarios reales (bloqueo legítimo).

**Impact:** denegación de servicio trivial sobre autenticación.

**Fix:** particionar por cliente: `AddPolicy("auth", ctx => RateLimitPartition.GetFixedWindowLimiter(ctx.Connection.RemoteIpAddress?.ToString() ?? "unknown", ...))`.

**Regression test:** dos clientes con IPs distintas → el agotamiento de uno no debe limitar al otro.

**[BUG-009] `ExecuteActionAsync`/`PerformMulliganAsync`: el conflicto del último reintento escapa como 500 (código muerto al final)**

- Severity: High · Confidence: High · Status: Confirmed (código)
- Location: `src/DotnetTCG.Application/Games/GameExecutionService.cs:156-168, 195-204`

**Evidence:** `catch (ConcurrencyConflictException) when (attempt < MaxRetries - 1) continue;` — en el intento 2 el filtro es falso → la excepción propaga; el `return Fail("Game.Conflict", ...)` posterior es **inalcanzable** (el bucle siempre retorna o lanza). El llamador recibe 500 ProblemDetails en vez de `Game.Conflict` 409, y en el hub, un fallo de invocación en vez del evento `{code}`.

**Failure scenario:** dos acciones simultáneas con 3 conflictos seguidos (partidas activas con ambos jugadores actuando).

**Fix:** capturar el conflicto sin filtro de intento (o `catch` final) y devolver `Fail("Game.Conflict")`.

**Regression test:** forzar `ConcurrencyConflictException` en el 3er intento → el resultado debe ser `Game.Conflict` (409), no excepción.

**[FE-002] Con el hub caído no hay recuperación: throw síncrono + overlay de carga bloqueante**

- Severity: High · Confidence: High · Status: Confirmed (código)
- Location: `src/DotnetTCG.Frontend/src/app/shared/services/websocket/game-signal.service.ts:100-105`; `src/DotnetTCG.Frontend/src/app/shared/services/api/game.service.ts:438-447`; `game-page.css:436-447`

**Regression test:** unit con `connection=null` → `reconnect()` no lanza y vuelve a conectar; `isLoading` queda en false.

**[FE-003] Espectador de una partida aún en lobby: error garantizado y sin navegación al arrancar**

- Severity: High · Confidence: High · Status: Confirmed (código, ambos lados)
- Location: `src/DotnetTCG.Frontend/src/app/features/lobby/pages/game-lobby/game-lobby-page.ts:179-183`; `src/DotnetTCG.Api/Hubs/GameHub.cs:208-224`; `src/DotnetTCG.Application/Games/GameExecutionService.cs:272-276`

**Evidence:** `JoinAsSpectator` llama `LoadGameStateAsync`, que devuelve `Game.NotFound` cuando `Snapshot == null` (estado `InLobby`), y **solo después** hace `AddToGroupAsync`. **Regression test:** hub: `JoinAsSpectator` antes del start → sin error y, tras `StartGame`, recibe `game-state`.

## C. Violaciones arquitectónicas

Sin violaciones de la regla de dependencias (verificado en `.csproj` y `using`): Domain puro, Application sin EF/ASP.NET, Infrastructure implementa abstracciones de Application, sin referencias inversas. Lo que sí aparece:

1. **[ARCH-001] Reglas de negocio fuera del Dominio:** la regla ACE SPEC ≤1 vive en `DeckService` (Application) y no en `RuleValidator` → el invariante es evitable (BUG-010). Es la única violación funcional del principio "las reglas se protegen sin importar quién invoque".
2. **[ARCH-002] Validadores registrados pero no usados:** `AddValidatorsFromAssemblyContaining<DeckService>` registra `CreateDeckValidator`/`AddCardValidator`, que ningún controlador inyecta (`AuthController` y `CardsController` sí inyectan los suyos) → validación muerta y 500s (BUG-003).
3. **[ARCH-003] Doble abstracción de reloj:** `IClock` (Application) + `TimeProvider` (Program/Hub) — convención aceptable pero convendría unificar.

## D. Riesgos de escalabilidad y rendimiento

- **[PERF-001] Confirmado:** `DeckService.ToDtoAsync` hace una query por carta (listar 10 mazos de 60 → ~600 queries) y `ListAsync` anida ese N+1.
- **[PERF-002] Confirmado:** `EfCardRepository.UpsertRangeAsync` = `FindAsync` por carta (import/seed de 146 → 146 queries en una transacción).
- **[PERF-003] Potencial:** `PushStatesAsync` refetcha lobby + estado + cartas por cada jugador y espectador en **cada** acción.
- **[PERF-004] Potencial:** paginación por offset (`page*pageSize`) con índice btree inútil para `ILIKE '%x%'` — aceptable con el volumen actual (146–3000 cartas), medir antes de crecer.
- **[PERF-005] Potencial:** sin rate limit en acciones de juego/hub (solo auth) → spam autenticado de CPU/DB.

## E. Cobertura de tests faltante

1. **[TEST-001] Los tests con DB se auto-omiten y cuentan como pasados** (BUG-013) — el gate puede dar verde con cobertura real mucho menor (ya ocurrió en esta auditoría).
2. **[TEST-002] Tests que enmascaran bugs:** `AttackPipelineTests.Resume_WithBenchSelection_Completes` (reusa el mismo `ctx`) y `AttackRegistryTests.Torment_BlocksOpponentNextAttack` (aserta en turno T, no T+1).
3. **[TEST-003] Sin tests para:** conflicto en el 3er reintento (409 vs 500), join tras salida del creador, delete de mazo en uso, nombre >100, authz de `start`, registro concurrente, rate limiter por cliente, `LeaveAsync` en partida en curso, ACE SPEC en `NewGame`, autorización de `PendingChoice`, pago de energía por tipo, y en el FE: el flujo lobby→tablero completo (el que descubrió FE-001).
4. Los tests de contrato del FE usan fixtures propios, no payloads reales del BE.
